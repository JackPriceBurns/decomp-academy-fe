# The assembly keeps the operand order

Thumb has two encodings for adding two registers. agbcc chooses between them
for a reason, and you can use that reason to work back to the source.

The two-operand form is the cheaper default. Here is `x + y` for the first two
arguments:

```asm
0        add       r0, r1
2        bx        lr
```

This means `r0 = r0 + r1`. The destination already holds the left operand, and
the sum has to end up in `r0` anyway. So one two-operand instruction covers the
whole expression.

Now swap the two operands in the source. The sum is the same number, but the
instruction is different:

```asm
0        add       r0, r1, r0
2        bx        lr
```

This means `r0 = r1 + r0`. This time the left operand is in `r1`, and the
result still has to end up in `r0`. The two-operand form can only write to the
register that holds the left side, so it no longer fits. gcc uses the
three-operand encoding instead and names `r0` twice: once as the right-hand
source and once as the destination.

So `add r0, r1, r0` tells you that the **left operand was the second
argument**. There is no cheaper way to encode that addition. When the
destination register of an `add` also appears as its last source, the source
code wrote that operand on the right.

Once `r0` holds the running total, every later term is added with the
two-operand form. Each `add` overwrites `r0` with the new total, because
nothing needs the earlier values again.

Read your target from the top. The first instruction tells you the operand
order, and the instructions after it each add to the total.

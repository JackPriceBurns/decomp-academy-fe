# The constant goes in the destination

Thumb's `and Rd, Rs` takes two operands and overwrites one of them: it computes
`Rd &= Rs`, so the old value of `Rd` is lost. There is no immediate form. The
instruction set has no `and r0, #7`, so every mask has to be loaded into a
register before the `and` can use it.

That leaves the compiler a choice: which register holds the mask, and which
holds the value. gcc 2.9 prefers to put the constant in the *destination*, the
register that the result has to end up in anyway. Here is a function that masks
its second argument:

```asm
0        mov       r0, #7
2        and       r0, r1
4        bx        lr
```

That is two instructions. The mask goes straight into `r0`, where the return
value has to end up. The value being masked stays untouched in `r1`, so nothing
is in the way.

Now look at what happens when the value being masked is already in `r0`,
because an earlier instruction put it there:

```asm
0        add       r0, #1
2        mov       r1, #63
4        and       r0, r1
6        bx        lr
```

The sum is in `r0`, and the register allocator can leave it there. So the mask
goes into the scratch register `r1`. The instruction is still `and r0, r1`, but
the roles have swapped: now `r0` holds the value and `r1` holds the mask. The C
operation is the same.

This listing also shows a difference between the two kinds of constant. `add`
carries its constant inside the instruction (`add r0, #1`), but the mask needs a
separate `mov`. `add`, `sub` and `cmp` have 8-bit immediate forms. `and`, `orr`,
`eor` and `bic` have none. So in Thumb, arithmetic constants and bitwise
constants look very different.

The third case is the one in your target, and it is the most common. When the
value being masked arrives as the *first* argument, it is already in `r0`, the
register the constant wants. So the compiler moves the value out of `r0` first.
An opening `mov rN, r0` is a clue for a decompiler: it tells you that the value
being masked came in as the first argument.

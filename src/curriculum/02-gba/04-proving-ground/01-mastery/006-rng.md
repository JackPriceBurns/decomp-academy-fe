# Where a game's randomness comes from

Almost every cartridge has a linear congruential generator (LCG). It keeps one
32-bit seed in RAM. On each call, the seed is multiplied by a large odd
constant, another constant is added, and the new value is written back over the
old one. It is four lines of C, and you can recognise it quickly in a listing.
The two constants are much too wide for a `mov`, so they go in the literal pool
next to the seed's own address.

The low bits of an LCG are close to useless. Bit 0 alternates on every call, and
bit 1 has a period of four. So the useful randomness is in the top bits. That is
why these routines almost always end by shifting the seed down, instead of
returning the whole seed.

Here is one of those generators, rolling a damage value:

```asm
0        push      {lr}
2        ldr       r2, [pc, #24] (->28)
4        ldr       r1, [r2, #0]
6        ldr       r0, [pc, #24] (->32)
8        mul       r0, r1
10       add       r0, #1
12       str       r0, [r2, #0]
14       lsr       r0, #24
16       mov       r1, #6
18       bl        __umodsi3-4
22       pop       {r1}
24       bx        r1
26       .hword    0
28       .word     gDamageSeed
32       .word     69069
```

Read the pool first. `.word gDamageSeed` is the global's address. It is printed
by name because it is a relocation. `.word 69069` is the multiplier. The addend
is 1, which fits in an 8-bit immediate, so it does not go in the pool. It is the
`add r0, #1`. Then `str r0, [r2, #0]` stores the new seed, and `lsr r0, #24`
keeps the top byte.

The `bl` is the problem. This machine has no instruction for `% 6`, so it
becomes a call to `__umodsi3`. The call also brings in `push {lr}`, `pop {r1}`
and `bx r1`. So a leaf function becomes a function that makes a call, only for
one modulo. On a 16.78 MHz ARM7 running from cartridge ROM, that wastes dozens
of cycles every time anything in the game needs a number.

So shipped code scales instead of dividing. Take a value that is already
uniform across some width, multiply it by the size of the range you want, and
shift the product back down by that same width. The result is inside the
range, and no division is needed. That is why your target has no `bl` at all.

## Your task

Write `func_08410b40` to reproduce the target assembly.

<!-- context -->
```c
extern u32 gRngSeed;
```

<!-- solution -->
```c
u32 func_08410b40(u32 range)
{
    gRngSeed = gRngSeed * 1103515245 + 12345;
    return ((gRngSeed >> 16) * range) >> 16;
}
```

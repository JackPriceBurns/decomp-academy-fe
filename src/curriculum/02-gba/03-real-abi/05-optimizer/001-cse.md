# Written twice, computed once

gcc 2.9 runs common-subexpression elimination before it allocates registers.
Suppose the same expression appears more than once in a straight run of code,
and nothing between the two copies could change its inputs. Then the compiler
evaluates the expression once and keeps the result in a register.

This matters for decomp because it removes information. Say a target computes
a value once and reads it twice. The C could have stored the value in a local,
or it could have written the expression out a second time. Both versions reach
the optimizer as the same internal graph, so both produce the same bytes. You
can pick whichever one reads better.

The pass does not always apply. A `bl` between the two uses forces a reload,
because the called function could have written to any memory. A store through
the same pointer the value was loaded from also forces a reload. A store
through a *different* pointer does not. gcc 2.9 treats two distinct pointers as
pointing to distinct objects, so it keeps the value it already loaded.

Here is `spread`, which uses `a | b` three times inside one ternary:

```asm
0        orr       r0, r1
2        sub       r1, r2, r0
4        cmp       r0, r2
6        ble       10 ~>
8        sub       r1, r0, r2
10     ~>mov       r0, r1
12       bx        lr
```

There is only one `orr`. Its result stays in `r0` for the rest of the function.
All three uses read it: the `sub r1, r2, r0` that builds the else value, the `cmp
r0, r2` that tests it, and the `sub r1, r0, r2` on the then side.

Here is the same function with the expression stored in a local first:

```asm
0        orr       r0, r1
2        sub       r1, r2, r0
4        cmp       r0, r2
6        ble       10 ~>
8        sub       r1, r0, r2
10     ~>mov       r0, r1
12       bx        lr
```

The two listings are identical, byte for byte. The local became a register that
the compiler was going to allocate anyway.

Your target does the same thing with a value that is loaded from an array and
then multiplied. The address calculation, the load and the `mul` each appear
once. Count how many later instructions read that one result.

# The pool keeps the order of the globals

A function that uses two different globals has two pool words. They are laid
out in the order the compiler first needed them. The function loads both
addresses first, then loads both values, then uses them.

That order records something the instructions do not. Here are two functions
that add the same two globals, written in opposite order in the source:

```asm
0        ldr       r0, [pc, #8] (->12)
2        ldr       r1, [pc, #12] (->16)
4        ldr       r0, [r0, #0]
6        ldr       r1, [r1, #0]
8        add       r0, r1
10       bx        lr
12       .word     gWarm
16       .word     gCool
```

```asm
0        ldr       r0, [pc, #8] (->12)
2        ldr       r1, [pc, #12] (->16)
4        ldr       r0, [r0, #0]
6        ldr       r1, [r1, #0]
8        add       r0, r1
10       bx        lr
12       .word     gCool
16       .word     gWarm
```

The instructions and the registers are the same in both. The only difference
in the whole function is which name is in which pool slot. On machines with
wider instructions, the operand order of a commutative add is usually lost
completely. Here the pool keeps it, so the diff checks those two rows and they
must be in the right order.

In practice, trace which register each pool word ends up in. Then read what the
arithmetic does to that register. In both listings above, `r0` gets the first
word and `r1` gets the second, and `add r0, r1` puts the global listed first on
the left of the `+`.

Your target does different things to its two globals, so the registers tell you
more than the pool order does. You still need both rows in the right places.

## Your task

Write `func_083295b0` to reproduce the target assembly.

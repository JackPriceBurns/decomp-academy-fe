# One address, a load and a store

When a function reads a global and writes it back, the compiler loads the
address once and keeps it in a register. Each pool access costs a word and an
`ldr`. Paying that twice for the same variable in the same stretch of
straight-line code would be wasteful, so the compiler doesn't do it.

`tickPre` increments a clock and returns the new value:

```asm
0        ldr       r1, [pc, #8] (->12)
2        ldr       r0, [r1, #0]
4        add       r0, #1
6        str       r0, [r1, #0]
8        bx        lr
10       .hword    0
12       .word     gClock
```

`r1` holds the address, and nothing changes it after that. `r0` holds the
value: it is loaded from memory, changed by the arithmetic, and stored back.
That is five rows of code for one variable, using one pool word.

Here is the same increment, written to return the *old* value:

```asm
0        ldr       r1, [pc, #8] (->12)
2        ldr       r2, [r1, #0]
4        mov       r0, r2
6        add       r2, #1
8        str       r2, [r1, #0]
10       bx        lr
12       .word     gClock
```

The old value must be kept after the increment, so it is copied into `r0`
before `r2` is increased. That adds one instruction. The instruction count
changes from odd to even, so the `.hword 0` disappears too. Both changes come
from the same small detail in the source. You would not predict either of them
from the C unless you know this rule.

When the result is not used, the two forms of the increment compile to exactly
the same five instructions. Nothing in the listing tells you which one was
written.

Your target keeps the base address in a register across a little more
arithmetic than these two functions do.

## Your task

# add, then adc

Adding two 64-bit values takes two instructions, and the hardware fixes their
order. `add` sets the carry flag when the sum of the low halves goes past 2^32,
and `adc` adds that carry to the sum of the high halves. The carry only moves
upward, so the low halves always go first:

```asm
0        add       r0, r2
2        adc       r1, r3
4        bx        lr
```

Two pairs come in, `r0:r1` and `r2:r3`, and one pair goes out, in `r0:r1`. That
is three instructions and no stack frame. Whenever you see `add rX, rY` followed
directly by `adc rX+1, rY+1`, read the two as one `+` on a 64-bit value, and
count it as a single addition.

Adding a constant looks less familiar. Thumb has no 64-bit immediate, so the
compiler has to build the constant in a full register pair. It builds it in
`r0:r1`, which is the pair that already holds the incoming argument. So the
argument is moved out first, and the addition appears in reverse order, with the
constant as the left operand:

```asm
0        mov       r3, r1
2        mov       r2, r0
4        ldr       r1, [pc, #12] (->20)
6        ldr       r0, [pc, #8] (->16)
8        add       r0, r2
10       adc       r1, r3
12       bx        lr
14       .hword    0
16       .word     1000
20       .word     0
```

`mov r3, r1` / `mov r2, r0` moves the argument out to `r2:r3`. Then both halves
of the constant are loaded from the literal pool. The value 1000 is larger than
the 8-bit immediate limit, so it needs a pool word. The high half is zero, but
it still gets its own `.word 0` instead of a `mov r1, #0`. That spends four
bytes of ROM on a word of zeros, because the compiler was already emitting a
pool load for the other half.

The `.hword 0` at address 14 is the usual alignment padding. The `bx lr` at 12
means none of it runs.

Your target runs the same two instructions on a value that the function has to
load first. The `.word` row tells you where that value is stored, and the
offsets from that address tell you which half is which.

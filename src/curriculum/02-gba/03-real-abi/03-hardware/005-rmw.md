# Turning one bit on

Hardware registers pack unrelated switches into one halfword. `DISPCNT` holds
the video mode, which backgrounds are on, whether sprites are enabled and half a
dozen other flags. Code that wants to change one of them has to leave the rest
alone. So it reads the register, ors in the new bits, and writes the result
back.

Here is a function that sets three interrupt-request bits in `DISPSTAT`:

```asm
0        ldr       r0, [pc, #8] (->12)
2        ldrh      r1, [r0, #0]
4        mov       r2, #56
6        orr       r1, r2
8        strh      r1, [r0, #0]
10       bx        lr
12       .word     67108868
```

These five instructions always have the same shape. The address is loaded once
into `r0` and stays there for the whole sequence, because both the load and the
store need it. `r1` holds the value read from the hardware. 56 is 0x38, the
three bits being set. It needs its own register, because Thumb's `orr` takes two
registers and no immediate. There is no way to write "or in 0x38" directly. So
every `|=` on this machine costs an extra instruction to put the mask in a
register.

A mask over 255 costs two instructions, plus the copy you saw when building a
stored value. gcc builds the constant in a scratch register with `mov`/`lsl`,
then moves it into the register the `orr` uses. All three instructions are in
the object file.

One caveat. A single read-modify-write like this compiles the same with or
without `volatile`. The source does one read and one write either way, so there
is nothing for the optimiser to merge. This shape does not prove the qualifier
was there. The double load from the previous lesson does.

Your target sets a bit too high to build with a single `mov`. Its register
address can be built without the pool.

## Your task

Write `func_08367e08` to reproduce the target assembly.
